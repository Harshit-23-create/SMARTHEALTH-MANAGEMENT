🛠️ Standard Feature Implementation Workflow (16 Steps)

Use this checklist whenever an interviewer asks you to add a feature to the project. Follow these steps in order.

1
Understand the Requirement
Ask: What does the user do? What does the system return? Any role restrictions? Edge cases?
2
Define Acceptance Criteria
Write 3-5 clear "given/when/then" statements. Example: "Given I'm logged in as Doctor, when I search for patient name, then I see matching records."
3
Find Related Code
Check App.jsx for routing. Check server.js for existing patterns. Check models/ for schemas. Never assume — read the code.
4
Design the API Contract
Method (GET/POST/PUT/DELETE), endpoint path, request body shape, response shape, auth required, error codes.
5
Update Schema if Needed
Add new fields to existing Mongoose model or create a new model in backend/models/. Always use timestamps: true.
6
Implement Backend Route
Add route to server.js following existing pattern: app.METHOD('/path', async(req,res)=>{try{...}catch(err){...}})
7
Add Auth Middleware
Import authmiddleware.js and add as second argument to protected routes: app.post('/route', authMiddleware, async(req,res)=>{...})
8
Add Frontend API Call
In the relevant page, import API_BASE_URL from '@/utils/api'. Use fetch() with proper headers including Authorization: Bearer ${token}.
9
Add UI Component
Add the form/display inside DashboardLayout. Use existing Tailwind classes for consistency. Follow the card pattern from other pages.
10
Handle Loading & Errors
Add useState for loading, error states. Show spinner during fetch. Show error message on failure. Handle empty states.
11
Add Route to App.jsx
If new page: import component, add <Route path="/new-path" element={<ProtectedRoute><NewPage/></ProtectedRoute>}/>
12
Add Nav Link
Add to navItems array in DashboardLayout.jsx: { key: "featureKey", path: "/path", icon: IconComponent }
13
Add to i18n.js
Add translation keys for all new UI text in all 3 languages (en, hi, es) in src/i18n.js. Use useTranslation() hook in component.
14
Test Manually
Start backend: cd backend && npm run dev. Start frontend: cd careflow-dashboard && npm run dev. Test each acceptance criteria. Check Network tab in DevTools.
15
Check for Regressions
Verify existing features still work: login, patient list, ambulance map. Run npm run lint. Run npm run test (vitest).
16
Explain to Interviewer
"I identified the files, defined the API contract, added the backend route with auth middleware, updated the schema, created the frontend component with proper error handling, tested, and verified no regressions."
🔍 Example 1: Server-Side Patient Search/Filtering

NEW FEATURE Currently search/filter is client-side only. Add server-side search so large databases can be queried efficiently.

Files to Modify

backend/server.js careflow-dashboard/src/pages/PatientManagementPage.jsx

Step 1: Update Backend GET /patients Route

// server.js — modify the existing GET /patients route app.get("/patients", async (req, res) => { try { // Read query params: ?search=john&status=Admitted&page=1&limit=6 const { search, status, page = 1, limit = 6 } = req.query; const query = {}; // Add search filter if provided if (search) { query.$or = [ { name: { $regex: search, $options: "i" } }, { disease: { $regex: search, $options: "i" } } ]; } // Add status filter if provided (and valid) if (status && status !== "All") { query.status = status; } const total = await Patient.countDocuments(query); const patients = await Patient .find(query) .sort({ createdAt: -1 }) .skip((page - 1) * limit) .limit(Number(limit)); res.json({ patients, total, page: Number(page), pages: Math.ceil(total / limit) }); } catch (error) { res.status(500).json({ message: error.message }); } });

Step 2: Update fetchPatients() in PatientManagementPage.jsx

// PatientManagementPage.jsx — update fetchPatients const fetchPatients = async (searchTerm = search, statusFilter = filter, pg = currentPage) => { try { setLoading(true); // Build query string const params = new URLSearchParams({ page: pg, limit: itemsPerPage, ...(searchTerm && { search: searchTerm }), ...(statusFilter !== "All" && { status: statusFilter }) }); const res = await fetch(`${API_BASE_URL}/patients?${params}`); if (res.ok) { const data = await res.json(); setPatients(data.patients || data); // backwards compat setTotalPages(data.pages || 1); } else { setPatients(fallbackPatients); } } catch { setPatients(fallbackPatients); } finally { setLoading(false); } };

Step 3: Debounce the Search Input

// Add debounce to avoid API call on every keystroke const debounceRef = useRef(null); const handleSearchChange = (e) => { const val = e.target.value; setSearch(val); clearTimeout(debounceRef.current); debounceRef.current = setTimeout(() => { setCurrentPage(1); fetchPatients(val, filter, 1); }, 400); // wait 400ms after typing stops };

60-Second Interview Explanation

"Currently, search is done client-side — the frontend fetches ALL patients and filters in memory. This doesn't scale. My fix was to move search to the backend by adding query string support to the GET /patients route using MongoDB's $regex operator, combined with mongoose's skip/limit for server-side pagination. On the frontend, I updated fetchPatients() to build a query string and added a 400ms debounce to avoid hammering the API on every keystroke. This is a standard pattern in production APIs."

🔔 Example 3: Persist Notifications to Backend

NEW FEATURE Currently notifications are lost on page refresh (in-memory only). Add MongoDB persistence.

Files to Create/Modify

backend/models/Notification.js NEW

backend/server.js careflow-dashboard/src/context/NotificationContext.jsx

Step 1: Create Notification.js Model

// backend/models/Notification.js — NEW FILE import mongoose from "mongoose"; const notificationSchema = new mongoose.Schema({ type: { type: String, required: true }, title: { type: String, required: true }, message: { type: String, required: true }, read: { type: Boolean, default: false }, userId: { type: mongoose.Schema.Types.ObjectId, ref: "User" } }, { timestamps: true }); export default mongoose.model("Notification", notificationSchema);

Step 2: Add Routes to server.js

// server.js — add notification routes import Notification from "./models/Notification.js"; import authMiddleware from "./middleware/authmiddleware.js"; // GET notifications for logged-in user app.get("/notifications", authMiddleware, async (req, res) => { const notifs = await Notification .find({ userId: req.user.id }) .sort({ createdAt: -1 }) .limit(50); res.json(notifs); }); // POST — create notification app.post("/notifications", authMiddleware, async (req, res) => { const { type, title, message } = req.body; const notif = new Notification({ type, title, message, userId: req.user.id }); await notif.save(); res.status(201).json(notif); }); // PUT — mark all read app.put("/notifications/read-all", authMiddleware, async (req, res) => { await Notification.updateMany({ userId: req.user.id }, { read: true }); res.json({ message: "All marked read" }); });

Step 3: Update NotificationContext to Persist

// NotificationContext.jsx — add API sync const push = useCallback(async (type, title, message) => { // Optimistic UI update (immediate) const localNotif = { id: Date.now(), type, title, message, time: new Date().toISOString(), read: false }; setNotifications(prev => [localNotif, ...prev]); // Then persist to backend try { const token = localStorage.getItem("token"); await fetch(`${API_BASE_URL}/notifications`, { method: "POST", headers: { "Content-Type": "application/json", Authorization: `Bearer ${token}` }, body: JSON.stringify({ type, title, message }) }); } catch { // Silent fail — notification still shows locally } }, []);

60-Second Interview Explanation

"The existing NotificationContext is in-memory — notifications disappear on refresh. To fix this, I created a Notification Mongoose model with type, title, message, read, and userId fields. I added three protected backend routes (GET, POST, PUT) using authMiddleware so only authenticated users access their own notifications. On the frontend, I used an optimistic update pattern: the UI updates instantly, then the backend call happens asynchronously. This way, even if the backend fails, the user still sees the notification immediately."
